# Qwen3-Omni 语音多模态预训练详解

> 本文档基于 Qwen3-Omni Technical Report，面向全双工多模态模型预训练/模态对齐项目，系统梳理语音相关的架构设计、数据构建、训练策略等关键内容。

---

## 一、整体架构概述

Qwen3-Omni 采用 **Thinker-Talker** 架构：

| 模块 | 架构 | 参数量 | 是否支持流式 |
|------|------|--------|------------|
| Audio Encoder (AuT) | Attention Encoder-Decoder | 650M | 是 |
| Vision Encoder | SigLIP2-So400M | 540M | 否 |
| Thinker | MoE Transformer | 30B-A3B | 是 |
| Talker | MoE Transformer | 3B-A0.3B | 是 |
| MTP (Multi-Token Prediction) | Dense Transformer | 80M | 是 |
| Code2Wav | ConvNet | 200M | 是 |

**核心设计理念：**

1. **Thinker** 负责文本生成（理解+推理），处理所有模态输入（文本/音频/图像/视频）
2. **Talker** 负责语音生成，接收 Thinker 的多模态高维表示，将文本 response 转为流式语音
3. Thinker 和 Talker 都采用 **MoE（混合专家）** 架构，提高并发和推理速度
4. **关键改进**：Talker 不再消费 Thinker 的高层文本表示，仅依赖音频和视觉多模态特征。原因：
   - 文本 token 和 embedding 信息等价，不需要重复输入
   - 多模态特征对语音生成更重要（保持韵律/音色等）
   - 解耦后允许外部模块（RAG、安全过滤器）介入 Thinker 文本输出

**对你的启示：** 如果你做全双工模型，可以考虑类似的"理解模块+生成模块"分离架构，理解模块大、生成模块小，这样能保证实时性。

## 二、音频编码器 AuT（Audio Transformer）

### 2.1 架构设计

AuT 是一个 **Attention Encoder-Decoder** 自回归模型，从零开始训练（trained from scratch），不依赖任何预训练权重。

**关键参数：**
- 参数量：约 **0.6B（6亿）**
- Token 速率：**12.5 Hz**（即每秒产生 12.5 个音频 token，每个 token 对应约 80ms 音频）
- 输入：音频的 Filter Bank 特征
- 下采样：使用 **Conv2D blocks** 在 attention 层之前对 filter bank 特征进行 **8倍下采样**

### 2.2 训练数据

AuT 在 **2000万小时** 有监督音频数据上训练，数据分布如下：

| 数据类型 | 占比 | 说明 |
|----------|------|------|
| 中英文伪标签 ASR 数据 | 80% | 大规模语音识别数据，用伪标签生成 |
| 其他语言 ASR 数据 | 10% | 覆盖多语言能力 |
| 音频理解数据 | 10% | 非语音的通用音频理解（环境音、音乐等） |

### 2.3 注意力机制

为了平衡**实时 prefill 缓存效率**和**离线音频任务性能**，AuT 使用：
- **Flash Attention** + **动态注意力窗口**
- 窗口大小覆盖 **1~8 秒** 的 query pattern

**这意味着：**
- 对实时流式输入，用较短的注意力窗口保证低延迟
- 对离线的长音频任务，用较长窗口获取更好的上下文理解

### 2.4 在 Qwen3-Omni 中的使用

在 Qwen3-Omni 中，只使用 AuT 的 **Encoder 部分** 作为音频编码器：
- 输入音频重采样到 **16kHz**
- 转换为 **128 通道 Mel 频谱图**（25ms 窗口，10ms 步长）
- 每帧音频表示对应约 **80ms** 原始音频信号

**对你的启示：**
1. 音频编码器可以单独预训练，用大规模 ASR 数据学到通用音频表示
2. 12.5Hz 的 token 率是一个不错的平衡点——既不太稀疏丢信息，也不太密集增加计算负担
3. 2000万小时的数据量对小团队不现实，但核心思路可以复用：以 ASR 数据为主 + 少量音频理解数据混合训练

## 三、预训练三阶段策略（核心）

Qwen3-Omni 的预训练分为三个阶段，逐步解锁模型能力：

### 3.1 Stage 1：编码器对齐阶段（Encoder Alignment）

**目标：** 让音频/视觉编码器的表示能够被 LLM 理解

**初始化：**
- LLM 部分：用 **Qwen3** 参数初始化
- 视觉编码器：用 **Qwen3-VL** 的编码器
- 音频编码器：用预训练好的 **AuT**

**训练策略：**
- **冻结 LLM 参数**，只训练编码器和 Adapter
- 两个编码器（视觉 + 音频）**分别训练**
- 训练顺序：先训练各自的 **Adapter**，再训练 **Encoder** 本身

**重要设计决策：** 他们放弃了 Qwen2.5-VL / Qwen2.5-Omni 中"Encoder + Adapter 联合训练、LLM 冻结"的做法。原因是：
> 如果 LLM 冻结不变，编码器可能会学习"补偿" LLM 的局限性，导致编码器的感知能力反而退化。

**对你的启示：**
- 第一阶段的关键是让编码器输出的表示"对齐"到 LLM 的语义空间
- Adapter 是轻量级桥梁模块，先训练它可以建立基本的映射关系
- 冻结 LLM 的目的是防止 LLM 在这阶段被"拖坏"（因为此时编码器还不成熟）
- 分开训练两个编码器可以避免干扰

### 3.2 Stage 2：通用训练阶段（General Stage）

**目标：** 全参数联合训练，增强多模态理解和交互能力

**训练配置：**
- **解冻所有参数**
- 总数据量：约 **2万亿 tokens（2T）**

**数据分布：**

| 模态 | Token 数量 | 占比 |
|------|-----------|------|
| 文本 | 0.57T | 28.5% |
| 音频 | 0.77T | 38.5% |
| 图像 | 0.82T | 41% |
| 视频 | 0.05T | 2.5% |
| 视频+音频 | 0.05T | 2.5% |

**注意：** 总和超过 100% 是因为部分数据有重叠或多标签。

**关键点：**
- 音频数据占比很大（38.5%），说明语音模态对齐需要大量数据
- 纯文本仍然是重要组成部分，防止语言能力退化
- 引入更多样的多模态数据和任务，增强跨模态交互能力
- 使用多样化的自然语言 prompt（而非单一 prompt），提升泛化能力和指令跟随能力

### 3.3 Stage 3：长上下文阶段（Long Context Stage）

**目标：** 提升模型处理长序列数据的能力

**配置变化：**
- 最大 token 长度从 **8,192** 提升到 **32,768**
- 增加长音频和长视频在训练数据中的比例

**效果：** 模型对长序列数据的理解能力显著提升

**对你的启示：**
- 三阶段设计是一种"从简到难"的课程学习（Curriculum Learning）思路
- 不建议一开始就全参数训练——先让编码器对齐，再联合优化
- 长上下文能力需要单独训练，不能指望 Stage 2 自然获得

## 四、多模态位置编码（TM-RoPE）

### 4.1 什么是 TM-RoPE

TM-RoPE（Time-aligned Multimodal Rotary Position Embedding）是 Qwen3-Omni 对位置编码的创新设计，将传统的 RoPE 分解为三个维度：

- **时间维度（Temporal）**：24 个 rotary angles
- **高度维度（Height）**：20 个 rotary angles
- **宽度维度（Width）**：20 个 rotary angles

### 4.2 不同模态的位置编码方式

| 模态 | 时间 ID | 高度/宽度 ID | 说明 |
|------|---------|-------------|------|
| 文本 | 三个维度共享同一 ID | 退化为一维 RoPE | 与普通 LLM 一致 |
| 音频 | 共享 ID + 绝对时间编码 | - | 每个时间 ID 对应 80ms |
| 图像 | 固定常量 | 按行列分配 | 只有空间信息 |
| 视频帧 | 动态时间戳 | 按行列分配 | 时间分辨率 80ms/ID |

### 4.3 音视频流的对齐方式

- 音频：每 80ms 一个时间 ID
- 视频：根据实际时间戳动态调整，也保持 80ms/ID 的分辨率
- 多模态拼接时：位置编号连续递增，后一个模态从前一个模态最大 ID + 1 开始

**与 Qwen2.5-Omni 的区别：**
- Qwen2.5-Omni 将音视频切成固定 2 秒的 chunk 再对齐
- Qwen3-Omni 直接用绝对时间 ID 对齐，支持任意时长的流式输入

**对你的启示：**
- 在做模态对齐时，位置编码是关键——不同模态需要在"时间轴"上对齐
- 80ms 的时间分辨率（12.5Hz）是音视频模态的统一锚点
- 如果你做全双工模型，需要考虑输入流和输出流的时间对齐问题

## 五、语音生成模块（Talker）的训练

### 5.1 Talker 架构

Talker 是一个 **MoE Transformer**（3B 总参数，0.3B 激活参数），负责将 Thinker 的理解结果转化为流式语音。

**语音生成流程：**
1. Talker 接收 Thinker 的多模态高维表示和对话历史
2. Talker backbone 消费当前帧的聚合 codebook 特征
3. 用 **线性头** 预测第 0 个 codebook（主码本）
4. **MTP 模块** 生成剩余的残差 codebook
5. **Code2Wav**（轻量因果 ConvNet）将 codec token 转为波形

**Codec 格式：** 使用 RVQ（Residual Vector Quantization）token，来自 Qwen3-TTS-Tokenizer-v2

### 5.2 Talker 四阶段训练

| 阶段 | 目标 | 数据 | 方法 |
|------|------|------|------|
| Stage 1：大规模预训练 | 建立多模态表示到语音的单调映射 | 数亿条带多模态上下文的语音数据 | Next-token prediction |
| Stage 2：持续预训练（CPT） | 缓解噪声数据引起的幻觉，提升语音质量 | 高质量数据 + 长上下文数据 | 高质量数据精炼 + 长上下文训练 |
| Stage 3：DPO 优化 | 提升多语言语音生成的泛化性和系统稳定性 | 多语言语音偏好对 | Direct Preference Optimization |
| Stage 4：说话人微调 | 使 Talker 能采用特定声音 | 高表现力多说话人数据 | Speaker fine-tuning |

### 5.3 各阶段详解

**Stage 1 - 大规模预训练：**
- 核心任务：学习从语义表示到语音的映射
- 同时学习根据上下文表达合适的韵律、情感、口音等
- 数据量级：数亿条（hundreds of millions）
- 问题：数据量大但不可避免有噪声和标注错误，导致幻觉

**Stage 2 - 持续预训练：**
- 使用高质量数据对抗 Stage 1 的噪声问题
- 同时进行长上下文训练，增强处理复杂输入的能力

**Stage 3 - DPO：**
- 构建多语言语音的偏好对（preference pairs）
- 用 DPO 算法优化，提升稳定性

**Stage 4 - 说话人微调：**
- 在 base model 上进行说话人微调
- 给每个说话人分配唯一的 index token
- 优化语音的自然度、表现力和可控性

**对你的启示：**
1. 语音生成模块的训练也是分阶段的：先量大→再质优→再 RL 优化→再个性化
2. DPO 在语音生成中也有用——可以用 WER 和停顿错误率来构建偏好对
3. 说话人身份和语音风格是可以解耦的，通过 token 索引来控制

## 六、跨模态联合训练的关键发现

论文专门设计了一组对照实验来验证"多模态联合训练是否会导致单模态能力退化"，结论非常有价值：

### 6.1 实验设计

训练了三个参数量完全相同的 30B-A3B 模型：
- **Qwen3-30B-A3B-Base**：纯文本模型
- **Qwen3-VL-30B-A3B-Base**：文本 + 视觉模型
- **Qwen3-Omni-30B-A3B-Base**：文本 + 视觉 + 音频模型

所有模型使用相同的训练 schedule、相同模态的相同数据集、相同的训练算力（FLOPs）。唯一区别是 Omni 模型额外加入了音频和少量音视频数据。

### 6.2 核心发现

1. **多模态联合训练不会导致语言能力退化**
   - Omni 模型在 MMLU、MMLU-Redux 等纯文本 benchmark 上与纯文本模型持平甚至更好

2. **文本模态显著提升视觉和音频性能**
   - 加入文本数据后，视觉和音频任务的表现大幅提升

3. **音频数据能提升视觉任务表现**
   - 加入音频数据后，MMMU（大学水平问题）和 OCR 相关任务的分数提升
   - 这说明不同模态之间存在**正向迁移**

4. **但视觉/音频对语言能力没有可测量的提升**
   - 跨模态迁移是非对称的：语言→视觉/音频有帮助，反向则不明显

### 6.3 具体数据对比

| 任务 | 纯文本模型 | VL 模型 | Omni 模型 |
|------|-----------|---------|----------|
| MMLU | 81.24 | - | **81.69** |
| SuperGPQA | 38.24 | - | **40.14** |
| EvalPlus | 69.70 | - | **73.96** |
| MMMU | - | 57.22 | **59.33** |
| MMStar | - | 67.2 | **69.6** |
| ChartQA | - | 87.12 | **87.52** |

**对你的启示：**
1. **大胆做多模态联合训练**——不用担心加入音频模态会损害已有的文本/视觉能力
2. **从预训练早期就混合多模态数据**，这是 Qwen3-Omni 的核心策略
3. 音频和视觉之间存在正向迁移，联合训练可能比单独训练效果更好
4. 保持文本数据的比例很重要——文本是多模态学习的"锚"

## 七、后训练（Post-training）

### 7.1 Thinker 后训练（三阶段）

| 阶段 | 方法 | 说明 |
|------|------|------|
| Stage 1 | SFT（监督微调） | 轻量级 SFT，弥合预训练表示与下游任务的差距 |
| Stage 2 | Strong-to-Weak 蒸馏 | 先离线蒸馏（教师模型生成 response），再在线蒸馏（学生生成、KL 散度对齐） |
| Stage 3 | GSPO（强化学习） | 全面提升各模态能力，使用规则奖励 + 模型奖励 |

**奖励信号设计：**
- **Rule-based Reward**：用于可验证任务（数学、编码、指令跟随），精度高、防 reward hacking
- **Model-based Reward**：用于无客观评估标准的任务，用 LLM（Qwen3）作为评判者，视觉任务用 Qwen2.5-VL

**蒸馏细节：**
- 教师模型：Qwen3-32B 或 Qwen3-235B-A22B
- 离线阶段：教师生成 response，学生学习
- 在线阶段：学生自己生成，logits 对齐教师

### 7.2 数据格式

所有训练数据统一使用 **ChatML** 格式，包括：
- 纯文本对话
- 视觉模态对话
- 音频模态对话
- 混合模态对话

**对你的启示：**
1. 后训练同样是分阶段的：SFT → 蒸馏 → RL
2. 蒸馏是小模型获得大模型能力的高效方法
3. 奖励信号可以混合使用规则和模型两种方式

## 八、流式推理与低延迟设计

### 8.1 端到端首包延迟

| 场景 | 延迟 |
|------|------|
| 纯音频输入 | **234ms** |
| 视频输入 | **547ms** |

### 8.2 关键优化

1. **Chunked Prefilling**：音频/视觉编码器沿时间维度输出 chunk，Thinker 处理完一个 chunk 后立即给 Talker 异步 prefill，同时处理下一个 chunk
2. **MoE 架构**：减少 KV cache 的 IO 消耗，提升生成 TPS 和并发能力
3. **Left Context Only Multi-Codebook Generation**：Talker 每生成一个 token，MTP 模块立即预测剩余 codebook，Code2Wav 立即合成波形——不需要等待足够的块上下文
4. **轻量级 MTP + ConvNet**：低 FLOPs，支持批量推理

### 8.3 生成实时因子（RTF）

| 并发数 | RTF |
|--------|-----|
| 1 | 0.47 |
| 4 | 0.56 |
| 6 | 0.66 |

RTF < 1 意味着生成速度快于实时播放速度，保证了流式体验。

**对你的启示：**
- 全双工模型的延迟优化是关键——首包 234ms 是一个很好的目标
- 异步 prefill + chunked processing 是降低延迟的核心手段
- RTF 必须 < 1 才能保证流式输出不卡顿

## 九、总结：构建语音多模态预训练系统的路线图

基于 Qwen3-Omni 的经验，如果你要做全双工多模态模型，建议的路线：

### Step 1：准备音频编码器
- 使用大规模 ASR 数据预训练一个音频编码器
- 或复用现有的预训练编码器（如 Whisper、HuBERT 等）

### Step 2：模态对齐（对应 S1）
- 冻结 LLM，训练 Adapter 和编码器
- 使用大量音频-文本配对数据
- 让编码器输出的表示能被 LLM 理解

### Step 3：联合训练（对应 S2）
- 解冻所有参数
- 混合文本、音频、视觉等多模态数据
- 保持文本数据的比例（约 30%）
- 使用多样化的 prompt 模板

### Step 4：长上下文扩展（对应 S3）
- 逐步增大序列长度
- 增加长音频/长视频数据的比例

### Step 5：后训练
- SFT → 蒸馏 → RL（GSPO/DPO）
- 语音生成部分额外做 DPO 和说话人微调

### 需要关注的关键指标
- **ASR WER**：语音识别准确率
- **首包延迟**：端到端从输入到第一帧输出的时间
- **RTF**：生成实时因子，必须 < 1
- **跨模态性能**：加入新模态后原有模态的性能是否退化
